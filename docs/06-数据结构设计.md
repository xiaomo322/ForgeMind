# ForgeMind 数据结构设计

**版本：V0.1**  
**状态：设计中；正在设计 Action / Observation 共同外层**

## 1. State 的作用

State 不是普通日志，而是 Agent Loop 的上下文载体，使 Agent 能在下一轮循环中知道当前目标、进度、已执行事实和验证结果。

## 2. State 概念模型（候选分组）

```text
ForgeMindState
├── task
├── progress
├── context
├── findings
├── actions
├── verification
└── permissions
```

## 3. 字段含义

| 区域 | 记录内容 |
|---|---|
| `task` | 用户问题、任务目标和完成条件 |
| `progress` | 当前阶段和任务进度 |
| `context` | 已查看文件、相关符号等任务上下文 |
| `findings` | 候选问题、怀疑问题和已确认问题 |
| `actions` | 已经发起和执行过的操作 |
| `verification` | 程序、已有测试和新测试结果 |
| `permissions` | 权限范围和用户确认情况 |

## 4. 事实来源原则

涉及客观执行事实的 State，应尽可能由 Runtime 根据 Tool 的实际结果更新，而不是由 Agent 自己声称。

```text
Agent 产生 read_file Action
  ↓
Tool 成功读取
  ↓
Observation 返回
  ↓
Runtime 更新 examined_files
```

如果 Tool 执行失败，不得把目标文件记录为已成功读取。

## 5. Action 与 Observation（既有候选，正在收束）

Action 至少需要能够表达：

```text
action_id
action_type
tool_name
arguments
target
reason
```

Observation 至少需要表达执行状态、结果内容或摘要、错误信息和相关元数据。

完整字段类型、枚举值和校验规则将在后续 Schema 设计阶段确定。

## 6. Action 的共同外层与工具参数（2026-09-14 教学草案）

Action 是 Agent 交给 Runtime 的请求契约。不同工具的业务参数不同，但 Runtime 对每次请求都需要执行关联、分类、路由和审计，因此采用共同外层包裹工具专属参数。

共同外层候选职责：

- `action_id`：唯一关联该次请求与后续 Observation。
- `action_type`：区分调用工具、询问用户、提出完成等决策种类；本章后续再确定各变体结构。
- `tool_name`：在工具调用变体中决定 Runtime 路由到哪个工具。
- `arguments`：保存该工具自己的结构化参数，并依据 `tool_name` 选择对应参数契约。
- `reason`：说明本轮为何选择该请求，供审查和上下文使用；不能替代参数或授权。

例如 read_file 与 run_command 共享 action_id、action_type、tool_name、reason，但 arguments 不同：read_file 需要 path/读取范围，run_command 需要 program/args/working_directory/timeout。

外层字段不能与工具参数重复表达同一事实而产生冲突。既有候选 `target` 是否保留尚未确认：若 path 已在 arguments 中，再在外层 target 保存另一份路径，可能出现两者不一致；需先证明 Runtime 存在统一检查或展示需求，再决定使用规范化派生字段还是移除重复输入。

Runtime 在边界一次性校验外层结构，再按 action_type 与 tool_name 校验对应变体；内部代码只处理已验证的数据。错误结果采用一致外层、机器可识别错误类别与必要详情，具体 Schema 后续逐步确定。

用户已正确回答：path 不应放共同外层，因为工具参数各不相同，应放在 read_file 的 arguments 中，由专属参数契约校验。该题通过。不在本节直接确定 Python 类或 JSON Schema 实现。

## 7. Action 变体与类型标识（教学草案）

并非所有 Action 都调用工具，因此 `tool_name` 和 `arguments` 不能作为每种 Action 都必填的共同字段。更准确的结构分为最小共同字段与按 `action_type` 区分的变体字段。

最小共同字段候选为 `action_id`、`action_type`、`reason`。当 `action_type=tool_call` 时，必须提供 `tool_name` 与该工具的 `arguments`；当类型为 ask_user 时，提供明确问题及等待回答所需内容；当类型为 propose_completion 时，提供结论、验证依据及未验证事项。具体名称仍待逐项确认。

`action_type` 是判别字段。Runtime 先读取该字段，再选择对应结构校验，使错误组合难以进入内部流程。例如 ask_user 同时携带 edit_file 参数属于不符合该变体契约的请求，应拒绝或按明确兼容规则处理，不能猜测 Agent 的真正意图。

初步形状示意：

```text
Action
├── 共同：action_id / action_type / reason
└── 变体
    ├── tool_call：tool_name / arguments
    ├── ask_user：question / ...
    └── propose_completion：summary / evidence / unverified
```

用户已正确回答：ask_user 不使用 Tool，因此不应强制包含 tool_name。Runtime 应按 action_type 校验对应变体字段，该题通过。字段内容、枚举命名与完成证据结构尚未定稿。

## 8. action_id 的生成责任（教学讨论中）

action_id 用于把 Action、Observation 和 State 中的执行记录关联起来，必须在一次任务内唯一且稳定。若完全由 LLM/Agent 自由生成，可能出现遗漏、重复、格式错误，Runtime 不能把重复编号对应到两次不同请求。

候选职责划分：Agent 输出决策内容；Runtime 接收并通过结构校验后，为被接受的请求生成系统 action_id，再进入权限和执行流程。若 Agent 输出仍携带自己的临时标识，可作为模型侧引用信息，但不能替代 Runtime 的权威执行标识。MVP 是否需要临时标识尚未确定。

校验失败、尚未成为有效 Action 的模型输出是否分配 action_id，需要与“每次尝试均可审计”的需求一起决定；也可使用独立 attempt_id 记录解析尝试，避免混淆有效 Action 与无效输出。当前不定稿该扩展。

用户回答重复 action_id 会使执行和进度混乱、可能卡住，方向接近但表示不理解。已讲解核心问题是关联歧义：两个不同请求共享标识后，Observation、状态更新、重试和审计无法可靠指向具体请求；是否卡住只是可能后果。该题记为经讲解，不算独立答对。

据此，当前设计倾向由 Runtime 生成并拒绝重复的权威 action_id，而不是信任模型保证唯一。该方向已形成设计结论；具体格式、跨任务唯一范围和无效尝试标识仍待定。

## 9. Observation 的共同外层（下一教学入口）

Observation 需要稳定关联 action_id，并明确请求处理状态、工具是否执行、结果或错误。成功、校验失败、权限拦截、工具失败等变体应共享可预测的外层，再按状态携带对应详情。

用户已正确回答：status=success 不能同时携带 FILE_NOT_FOUND，因为成功与文件不存在互相矛盾。该题通过。

## 10. Observation 的结果变体（教学草案）

采用一个明确状态作为判别字段，使每个 Observation 只符合一种结果结构，避免 success=true、error 非空等组合矛盾。共同候选字段为 action_id 和 status；时间、工具名等是否进入共同外层后续按实际消费需求决定，避免重复。

概念变体：

- `success`：请求执行成功，必须有 result，不携带 error。
- `rejected`：Runtime 在调用 Tool 前因参数、权限或安全规则拒绝，必须有 error，工具未执行。
- `failed`：Tool 已被调用但未完成目标，必须有 error；是否产生部分副作用需在详情中按事实表达。

超时、用户取消、等待确认和测试用例失败是否独立为顶层状态，需结合控制流与 Tool 结果继续设计，当前不强行塞入上述三类。错误至少需要稳定的机器可识别 code、人类可读 message，以及必要 details；Agent 不依赖随意变化的 message 文本分支决策。

`rejected` 与 `failed` 的区别保留了处理阶段和工具是否执行。参数缺失属于 rejected，而文件读取时发现不存在属于 failed。测试成功运行但用例失败不能简单等同于 Tool 调用失败，后续单独设计 run_tests 的 result。

用户正确指出区分 rejected、failed、success 要看工具执行情况，但将缺少 path 误判为 failed。已纠正：Runtime 在边界校验发现必填参数缺失，拒绝请求且不调用 Tool，因此属于 rejected。该题记为判断原则理解、具体分类经纠正，不算完全独立答对。

补强规则：`rejected` 表示 Action 没有通过 Runtime 的执行入口；`failed` 表示 Action 已通过入口并调用 Tool，但 Tool 未完成目标；`success` 表示 Tool 完成其契约目标。不能仅凭是否出现错误字样判断。

用户已正确回答：edit_file 参数完整但 Runtime 因缺少授权在调用前拦截，属于 rejected，Tool 未执行。该巩固题通过，rejected 与 failed 的阶段边界已掌握。状态命名和完整枚举仍未定稿。

## 11. Tool 执行状态与业务检查结果（教学草案）

Observation 顶层 status 描述请求/Tool 是否完成其契约目标，不一定等同于被检查对象是否符合预期。run_tests 的契约目标是运行测试并返回真实结果；如果测试运行器正常完成并报告 3 个通过、2 个失败，Tool 已成功取得测试结果，顶层可为 success，而 result 内的 test_outcome 为 failed。

概念示意：

```text
Observation.status = success
result.test_outcome = failed
result.passed = 3
result.failed = 2
```

若 pytest 未找到、进程无法启动或结果无法按契约取得，则属于 Tool 未完成目标，顶层为 failed。测试用例失败时退出码常为非零，但不能仅凭非零退出码把 Tool 层统一判为 failed；Runtime/适配器需按照已配置运行器契约解释结构化结果。

同样，search_code 成功搜索并返回 0 条匹配属于 Tool success，匹配数量为 0；是否足以支持 Agent 结论由后续决策判断。该分层避免把“执行检查成功”和“检查对象通过”混为一谈。

用户已正确回答：pytest 正常运行 5 条、其中 2 条失败时，Observation 顶层 status 为 success，result.test_outcome 为 failed，因为工具成功取得了部分用例失败的真实结果。该题通过。具体测试结果字段与未知统计表达仍未定稿。

## 12. State 的事实区与判断区（教学入口）

State 不能作为任意内容混写的字典。首要边界是区分 Runtime 根据实际执行记录维护的客观事实，与 Agent 根据事实提出的判断或推测。

候选分区延续既有模型：task 保存用户目标与完成要求；actions 保存 Action/Observation 关联历史；context 保存实际取得的任务相关上下文及版本/范围；verification 保存程序与测试证据；permissions 保存用户授权、拒绝及范围；findings 保存 Agent 的待验证、已支持或已否定判断；progress 保存当前流程阶段和等待状态。

同一信息不在多个区域由不同角色随意覆盖。Runtime 负责追加或更新可由执行证据确定的记录；Agent 可提出 findings 和下一步决策，但不能把推测直接写成已验证事实。用户回答形成任务要求或授权记录时，也由 Runtime/应用层按明确规则落入对应区域。

State 中既需要保留事件历史，也需要供 Agent 快速读取的当前视图。是否采用事件日志加派生视图、各字段是否可变及持久化方式后续设计；本节先确定语义归属。

用户已正确回答：Agent 推测“discount 传入值错误”进入 findings，run_tests 实际返回“2 条失败”进入 verification；判断依据是推测与实际执行证据的来源不同。该题通过。

## 13. 历史记录与当前视图（教学草案）

State 既要回答“曾经发生过什么”，也要回答“当前有效状态是什么”。只保留当前值会丢失调查过程，只保留完整事件列表则会让每轮 Agent 重放全部历史并自行推导当前状态。

候选分工：actions 保存按顺序追加的请求与结果历史；context/findings/verification/permissions/progress 提供经过规则更新的当前视图，同时保留必要来源引用。例如旧测试失败后修复并重测通过，历史中两次结果都保留，当前 verification 不能删除旧失败，也不能只显示旧失败；应指出最新相关验证及其 action_id、测试范围和时间/版本依据。

“最新”不自动等于“有效”：如果测试通过后文件再次修改，该测试仍是历史事实，但不再足以证明当前代码通过。当前视图需要把验证证据与被验证代码版本或相关变更关联。具体版本模型、时间字段和派生算法后续设计。

Agent 的旧推测被证据否定时，findings 保留状态变化及依据，而不是删除成从未提出；本轮上下文可只提供当前有效结论和必要历史摘要。

用户已正确回答：不删除第一次失败记录，当前视图表达修改后测试成功。补充限定：应写为“最新且仍适用于当前代码版本的相关测试通过”，并引用验证范围和 action_id，不能扩大为整个项目正确。该题通过。

完整上下文保存在 State，不等于每轮把全部原始历史提供给 Agent；上下文整理层可提供当前视图和必要历史摘要，完整事件仍用于追踪与审计。

## 14. progress 任务状态（教学草案）

progress 需要明确任务当前能否继续、正在等待什么以及是否已终止。候选状态：RUNNING（循环可继续）、WAITING_USER（保存待确认/待回答内容并暂停）、COMPLETED（完成要求已接受）、BLOCKED（无可行路径并记录原因）、CANCELLED（用户取消）。达到步数上限是否归入 BLOCKED 或独立状态后续决定。

状态转换由 Runtime 根据有效事件和规则执行，Agent 可以提出 ask_user、propose_completion 或报告阻塞，但不能直接把 State 强制改成 COMPLETED。WAITING_USER 收到回答后也不一定完成：Runtime 记录回答并根据其含义恢复 RUNNING、继续等待或进入终止状态。

概念流转：

```text
RUNNING → WAITING_USER → RUNNING
RUNNING → COMPLETED
RUNNING → BLOCKED
RUNNING / WAITING_USER → CANCELLED
```

状态字段不能替代详细原因和待处理记录。例如 WAITING_USER 还需关联具体问题或待授权操作；BLOCKED 需要已验证的阻塞原因。具体枚举、恢复策略和持久化后续定稿。

用户已正确回答：等待修改授权时属于 WAITING_USER；用户拒绝后任务不必立即结束，可以评估其他方式，确无办法或成功完成时才进入相应终止状态。该题通过。

补充边界：其他方式必须遵守用户拒绝的对象和意图，不能通过换 Tool、改路径或拆小操作绕过同一限制。可行替代方案若包含新的受控操作，仍需单独检查授权。用户取消则进入 CANCELLED；成功且满足完成标准才进入 COMPLETED；确无符合约束的路径才进入 BLOCKED。

## 15. permissions 授权记录（教学草案）

权限不能只保存 `allowed=true/false`，因为用户通常授权或拒绝的是一个具体操作范围。候选记录需要表达：关联的任务与待确认请求、决定（允许/拒绝）、操作类型、目标、参数或范围、作出决定的来源和当前是否仍适用。时间与版本字段后续设计。

例如“允许修改 src/pricing.py 中指定片段”不能解释为允许删除该文件、修改其他文件或运行 cleanup.py。若确认后文件版本、修改内容或作用范围变化，Runtime 重新判断是否仍被原授权覆盖。

拒绝记录同样有范围：拒绝一次具体替换不必自动等于永远禁止该文件的一切修改；但 Agent 不得把实质相同的操作换一种表达反复请求或绕过。若用户明确表达更宽的禁止意图，记录应忠实覆盖该范围。

Runtime 使用结构化授权事实做执行判断；给 Agent 的摘要帮助合理规划，但不是权威权限来源。授权记录应与 action_id 或待确认标识关联，避免把用户回答应用到错误请求。

用户已正确回答：只允许修改 pricing.py 一处返回语句的授权不能用于删除整个文件，因为操作类型和权限范围不同。该题通过。字段名与匹配算法未定稿。

## 16. task 任务定义（教学草案）

task 需要同时保留用户原始请求与系统当前理解，不能让 Agent 的总结覆盖原话。候选内容包括：Runtime 生成的 task_id、original_request、normalized_goal、scope、acceptance_criteria、constraints，以及后续用户澄清形成的 requirement_updates。具体字段名与是否嵌套后续确定。

`original_request` 是不可覆盖的来源记录；`normalized_goal` 是便于执行的任务理解，必须可随澄清修正并保留依据。`scope` 表示本任务处理边界；`acceptance_criteria` 表示达到什么证据才可提出完成；`constraints` 保存明确限制，例如不得改动某目录。权限另在 permissions 记录，避免把目标约束与具体授权混成一个布尔值。

例：原话“价格没打折，帮我修复”保留不变；系统可整理目标为“定位并修复会员折扣未生效”，但优惠券叠加方式尚不明确时不能自行写入完成标准，应询问用户并追加澄清记录。

任务理解是可修正的解释，不是客观原文。最终报告需能对照用户原始请求、有效澄清和完成标准，避免只完成 Agent 自己改写后的目标。

用户已正确回答：不能用 normalized_goal 覆盖 original_request，否则连续改写会丢失最初任务目标和上下文。该题通过。original_request 作为来源记录保留，normalized_goal 可基于用户澄清更新并保留变化依据。

## 17. findings 判断生命周期（教学草案）

findings 保存 Agent 对问题原因或相关性的判断，不只是一组无状态文本。候选记录至少表达 finding_id、statement、status、evidence_refs、created_from_action，以及状态变化历史或原因。具体字段名后续确定。

候选状态可先理解为：SUSPECTED（待验证推测）、SUPPORTED（已有支持证据但未达到确认标准）、CONFIRMED（证据足以确认）、REJECTED（新证据否定）。是否需要 UNKNOWN/CANDIDATE 等更细状态，待 MVP 实际流程证明必要再增加。

## 18. verification 验证证据结构（教学草案）

verification 不能只存“测试通过”一句结论，需要表达证据来源与适用范围。候选记录包括 verification_id、kind（测试/程序运行/静态检查等）、action_id、target、outcome、summary/details、artifact_or_code_version，以及是否仍适用于当前状态。时间字段和具体类型后续确定。

例如测试记录需区分实际测试目标、运行是否完成、用例结果与失败详情；顶层 Observation success 不替代 verification.outcome。验证目标只覆盖 tests/test_pricing.py 时，不能描述为整个项目所有测试通过。

验证证据与被验证版本关联。测试后相关代码再次修改，旧结果仍保留为历史证据，但当前适用性应失效或标记待重新验证。是否自动计算 affected scope，需要结合文件与依赖关系逐步设计，MVP 可先采用保守规则。

完成判断引用 verification 记录，而不是复制一条无法追踪的“已验证”文本。证据不足或无法运行时也保留真实状态，例如 NOT_RUN、PARTIAL、FAILED、PASSED 等候选结果；枚举尚未定稿。

## 19. 完成标准与证据映射（教学草案）

task.acceptance_criteria 不应只是一段无法检查的总描述。每条标准需要唯一标识、内容、当前状态及 supporting_evidence_refs / missing_evidence，使 Agent 和 Runtime 能逐项说明满足、未满足或无法验证。

候选状态：PENDING、SATISFIED、UNSATISFIED、UNVERIFIED。SATISFIED 必须引用仍适用的 verification、用户澄清或其他直接证据；UNVERIFIED 表示尚无充分证据，不等同于失败；具体枚举后续定稿。

propose_completion 应引用各条完成标准及证据，并列出未验证事项。Runtime 可确定性检查引用是否存在、证据是否仍适用、是否有待处理 Action；Agent 负责解释证据与业务目标的关系。若标准需要用户判断，则进入 ask_user / WAITING_USER，而不是伪造确定结论。

## 20. 第一版 State 流转示例（教学中）

以下价格折扣任务用于验证各分区能否支撑闭环，不代表项目真实运行结果。

- task：保留 original_request“价格没有打折，帮我修复”，形成待澄清/可修正的 normalized_goal、scope 与 acceptance_criteria。
- progress：RUNNING。
- actions/context/findings/verification：初始为空。
- permissions：保存当前项目范围及已有权限规则，不预先记录尚未给出的修改授权。

### 阶段二：调查

Runtime 为搜索和读取请求生成 action_id，并把 Action/Observation 追加到 actions。成功读取的路径、范围和版本进入 context。Agent 基于证据在 findings 提出“调用方可能传入错误折扣”为 SUSPECTED，并引用相关搜索/读取记录；测试异常进入 verification，而非直接确认原因。

### 阶段三：修改与确认

### 阶段四：验证与完成

run_tests 与实际调用验证分别形成 Observation 和 verification 记录。Agent 将证据映射到每条 acceptance_criteria；只有必需标准均有仍适用证据，或用户明确接受特定未验证范围，才提出完成。Runtime 校验引用与待处理状态后将 progress 转为 COMPLETED。

### 跨分区引用原则

分区不是彼此孤立的副本：actions 保存事件来源，context/findings/verification/permissions 通过稳定标识引用相关记录。相同内容不在多处由不同角色重复输入；当前视图由历史与规则派生，并保留依据。

本示例暴露的待定设计包括：task 澄清记录、文件/代码版本标识、证据失效算法、用户回答标识、状态时间字段及持久化方式。下一步先检查 State 更新的原子边界，再决定第一批正式 Schema。

## 21. State 更新的一致性边界（教学草案）

一次已确认事件可能同时影响多个分区。edit_file 成功后，需要原子地或通过可恢复事务式流程完成：追加 Action/Observation 历史、更新 context 的文件版本、标记相关 verification 失效/待重验、更新 acceptance_criteria 当前状态，并推进 progress。不能只更新其中一部分后让 State 长期暴露矛盾状态。

例如文件已实际修改，但 State 只追加修改成功、仍把旧测试标为当前有效，会导致 Agent错误提出完成。反过来，工具实际修改成功但 State 写入失败，也不能盲目重试 edit_file，以免重复或覆盖新变化；Runtime 应先核对目标文件并恢复记录。

“原子”在此指逻辑上要么整组状态转换生效，要么能检测未完成并恢复，不等于跨文件系统、数据库和外部进程天然拥有单一事务。MVP 可先采用单进程状态更新、写前后版本核对和恢复标记，具体存储与事务机制后续实现时确定。

State 更新规则应由 Runtime/状态管理代码执行，Agent 提供决策与判断建议，不能任意同时改写多个权威分区。

用户已正确回答：不能直接重复 edit_file，应先检查当前文件是否已更新成功，再决定是否执行。该题通过。补充核对内容包括当前文件内容/版本、原修改是否已生效及是否存在其他新变化；据此补全 State 或交给 Agent 重新评估。

## 22. 从概念模型进入正式 Schema

前述章节已明确主要语义边界，下一步按 Action → Observation → State 的顺序形成第一版语言无关 Schema。Schema 不只是字段清单，还规定字段类型、是否必填、允许值、不同变体的组合约束及错误语义，使 Runtime 能在系统边界确定性校验。

首个目标是 ToolCallAction：共同字段与 tool_call 专属字段、字符串非空、arguments 为结构对象，并根据 tool_name 继续选择工具参数契约。Runtime 生成 action_id 的时点会影响“Agent 原始输出”和“已接受 Action”是否使用两个模型，下一节先区分这两个阶段。

设计顺序遵循输入/输出分离：AgentDecision 是尚未被 Runtime 接受的外部输入；AcceptedAction 是通过校验并获得权威 action_id 的内部记录。二者不能用同一模型强迫 Agent 预先填写 Runtime 生成字段。

用户对为何 AgentDecision 不应必填 Runtime 生成的 action_id 回答不知道。已讲解输入字段所有权：若要求 Agent 填写，会把唯一性责任重新交给模型，造成遗漏、重复或与 Runtime 编号冲突；Runtime 也无法区分哪个值权威。该点记为经讲解，不算独立答对。

确定流程：AgentDecision 不包含权威 action_id；Runtime 先校验决策结构，通过后生成 action_id 并构造 AcceptedAction；Observation 引用 AcceptedAction.action_id。无效输出若需追踪，使用独立尝试记录，不占用或冒充有效 Action 标识，具体机制后续定稿。

用户已正确回答：AcceptedAction 必须包含 Runtime 生成的权威 action_id，因为它是要进入执行与结果关联的正式记录；AgentDecision 类似等待系统分配单号的申请。该巩固题通过。

## 24. ReadFileArguments 第一版字段规则（教学草案）

| 字段 | 类型/约束 | 必填 | 暂定行为 |
|---|---|---|---|
| `path` | 非空相对路径字符串 | 是 | 相对任务项目根目录解析，Runtime 另做授权与真实路径边界检查 |
| `start_line` | 正整数，从 1 开始 | 否 | 缺省从第 1 行开始 |
| `max_lines` | 正整数且不超过系统上限 | 否 | 缺省使用受控分段大小，不默认无上限读取全文 |

具体默认分段行数和硬上限需结合单行长度与输出字节限制测试后确定，本节不凭空设定数值。文件编码参数是否开放也暂缓，MVP 倾向统一 UTF-8 并对解码错误明确反馈。

## 27. EditFileArguments 第一版字段规则（教学草案）

| 字段 | 类型/约束 | 必填 | 暂定行为 |

用户选择方案 B：expected_version 必填，理由是更加严谨。该设计决定确认。具体含义是 edit_file 必须基于先前读取取得的版本；执行写入的临界位置再次检查版本，不一致则停止旧方案。Runtime 可提前检查，但不能只依赖早于实际写入的检查。

## 28. EditFileResult 第一版字段规则（教学草案）

成功结果候选字段：path、before_version、after_version、replacement_count、diff。首版精确替换要求 replacement_count=1；diff 是基于实际写入前后内容生成的变化，不使用 Agent 请求中的预览冒充执行结果。

版本冲突、0/多处匹配、权限拦截发生在实际写入前时，目标未被本次操作修改；根据检查归属形成 rejected 或 failed，但必须明确工具是否执行。临时文件失败、替换结果不确定等情况按已确认事实返回，不使用 EditFileResult 成功结构。

成功后 Runtime 使用 before/after 版本和 diff 更新 actions/context，并使关联旧 verification 失效。diff 用于审查，不替代重新读取或测试。

用户对 success 但前后版本相同、diff 为空是否有效回答不知道。已讲解：edit_file 的契约目标是产生指定内容变化；相同版本与空 diff 没有证明任何修改，和 success 矛盾。若请求本身新旧相同，应在执行前拒绝为 NO_CHANGE_REQUEST；若执行层返回该组合，应视为结果契约违规并核对文件，不能更新为成功修改。该点记为经讲解。

## 31. AskUserDecision / AcceptedAskUserAction 第一版字段规则

AskUserDecision 用于缺少必须由用户提供的需求、选择或信息时暂停循环。第一版候选字段：action_type 固定 ask_user、reason 非空、question 非空；options 为可选的非空字符串列表，仅在选项确实互斥且足够表达选择时使用。权限确认可由 Runtime 根据受控 ToolCall 主动生成等待记录，不依赖 Agent 构造 AskUserDecision。

AgentDecision 不含 action_id。Runtime 校验并接受后生成 AcceptedAskUserAction，加入 action_id、task_id，并将 progress 转为 WAITING_USER，同时创建与该 action_id 关联的 pending interaction。重复问题与已回答/已拒绝事项需结合 State 规则拦截，不能靠模型记忆。

`reason` 解释为什么需要询问，`question` 是实际展示给用户、需要回答的内容，两者不能互相替代。问题必须足够具体，不能把多个无关决定塞进一个模糊问题。用户回复作为独立记录关联该 action_id，不能覆盖原问题；恢复后由 Runtime 更新 task/permissions 等权威分区。

## 32. UserResponseRecord 第一版字段规则（教学草案）

## 33. PermissionDecisionRecord 第一版字段规则（教学草案）

权限确认虽然会向用户提问，但结果具有执行授权语义，不能只作为普通自由文本回答。候选独立记录包括 permission_decision_id、task_id、request_action_id / pending_permission_id、decision（APPROVE/REJECT）、authorized_operation、authorized_target、authorized_scope、raw_response，以及与文件版本/操作摘要绑定的信息。

Runtime 在拦截受控 ToolCall 时创建 pending permission，保存实际待执行程序/参数或修改 diff、目标、版本和风险说明。用户决定必须关联这份记录；APPROVE 只允许匹配范围内的原操作，REJECT 阻止该操作。Agent 不生成或扩展授权范围。

若 ToolCall 内容、文件版本、参数、工作目录或影响范围变化，Runtime 重新比较授权；超出原范围则创建新确认。相同自然语言“同意”不能在没有明确 pending_permission_id 时任意应用到某个操作。

普通需求回答更新 task/findings，权限决定更新 permissions；两者都保留 raw_response，但使用不同结构和处理规则。用户一次回答同时包含业务澄清和授权时，Runtime/交互层需明确拆分并记录来源，不能只保存一个模糊布尔值。

## 34. ProposeCompletionDecision 第一版字段规则（教学草案）

若存在 UNVERIFIED 必需标准，Agent 可以提出受限结论或请求用户接受风险，但 Runtime 不直接进入 COMPLETED。用户接受后仍保留 UNVERIFIED 状态和独立决定记录。若证据引用不存在、已过期、标准遗漏或仍有待处理 Action，完成提议被拒绝并返回明确原因。

Runtime 的检查不能证明所有业务解释正确；它验证记录一致性和最低完成条件，Agent/用户负责需要语义判断的部分。最终报告根据已接受完成记录生成，区分事实、推断和未验证风险。

## 35. 统一 SchemaValidationError（教学草案）

所有 AgentDecision 与工具 arguments 的结构校验应使用一致错误形状，使 Agent 能确定性修正请求。候选字段：code（稳定机器码）、message（人类可读说明）、field_path（错误字段路径，可为空）、details（必要结构化详情）。原始模型输出是否完整保存需考虑敏感信息与日志策略，不能默认塞入普通错误消息。

候选 code 包括 MISSING_FIELD、INVALID_TYPE、INVALID_VALUE、UNKNOWN_FIELD、INVALID_COMBINATION。多个独立错误可一次返回列表，减少逐字段往返；但数量和内容需要限制，避免错误输出过大。

未知字段有两个方案：A 忽略未定义字段；B 严格拒绝。当前推荐 B，因为忽略字段可能让 Agent 误以为某项限制或参数已经生效，例如提交 `recursive=true` 而工具实际忽略，导致请求含义与执行行为不一致。后续新增字段时通过明确的可选字段和兼容策略扩展，不依赖静默忽略。

错误 message 可调整措辞，Agent 的程序化分支应依据 code 与 field_path；details 不暴露内部堆栈或敏感路径。Schema 校验失败发生在 AcceptedAction 生成前，不产生权威 action_id；若需审计，使用独立 attempt 记录。

用户选择方案 B：未知字段严格拒绝，理由是静默忽略会造成大量无效行动。该设计决定确认。Runtime 返回 UNKNOWN_FIELD，不执行请求；后续兼容性通过正式增加可选字段或迁移规则实现。

下一步比较 Python 中手写 dataclass 校验与使用 Schema 校验库的实现边界；在选择第三方库前以官方文档核实当前能力与版本，不凭记忆定技术栈。

## 36. Python Schema 实现方式比较（教学草案）

本节只选择数据契约的实现方向，尚未安装依赖或编写 Schema 代码。项目当前没有 pyproject.toml、requirements 文件或锁文件，因此还不能声称已经选定或安装了某个 Pydantic 具体版本。

### 方案 A：标准库 dataclass + 手写校验

Python 官方文档把 dataclass 定位为根据字段注解自动生成 `__init__`、`__repr__` 等方法的工具。它适合减少内部数据类的样板代码，但 ForgeMind 还需要自行实现：未知字段拒绝、必填字段检查、嵌套结构校验、`action_type` 分支选择、多个错误汇总、错误路径以及 JSON Schema 生成。

这不是无法实现，而是契约规则会分散在构造函数、校验函数和序列化代码中。每增加一个 Action 或 Tool 参数类型，都要持续维护这些基础能力。

官方依据：https://docs.python.org/3/library/dataclasses.html

### 方案 B：Pydantic BaseModel

Pydantic 当前官方文档提供了与 ForgeMind 需求直接对应的能力：

- `ConfigDict(extra='forbid')` 会把未定义输入作为 ValidationError，而不是静默忽略；
- discriminated union 可以依据共同标签字段选择唯一结构，适合用 `action_type` 区分 tool_call、ask_user 和 propose_completion；
- ValidationError 提供 `type`、`loc`、`msg`、`input` 等结构化错误详情，可转换为统一 SchemaValidationError；
- 模型可以生成 JSON Schema，后续可用于约束模型输出及生成协议说明。

官方依据：

- https://docs.pydantic.dev/latest/api/config/
- https://docs.pydantic.dev/latest/concepts/unions/
- https://docs.pydantic.dev/latest/errors/errors/
- https://docs.pydantic.dev/latest/concepts/json_schema/

### 当前技术判断

当前推荐方案 B。ForgeMind 接收的是 Agent/模型产生的外部结构化数据，Runtime 边界需要确定性验证；Pydantic 已提供的严格额外字段、标签联合类型和结构化错误能直接支撑已经确认的协议。dataclass 仍可用于完全受控的内部对象，但首版不同时建立两套相似数据模型，以免产生转换和规则漂移。

需要区分两个“严格”：`extra='forbid'` 负责拒绝未知字段，`strict` 模式负责限制类型转换。前者已经由设计决定；后者不能因名称相似而自动开启，需用具体输入例子继续确认。

用户选择方案 B：使用 Pydantic 作为 Runtime 边界 Schema，理由是 Runtime 需要统一、确定地校验 Agent 产生的数据。该技术方向确认。dataclass 可在未来用于完全受控的内部数据，但不承担首版外部输入边界校验。

当前只确认库的方向，尚未创建依赖配置、固定具体版本或编写实现。下一步确认类型转换策略，再把已确认规则整理为第一组可实现模型。

## 37. 类型严格模式（教学草案）

未知字段策略和字段类型策略是两个独立问题：

- `extra='forbid'` 处理“Schema 中没有这个字段”；
- strict 类型校验处理“字段存在，但值的类型不符合契约”。

例如 ReadFileArguments 规定 start_line 为整数，Agent 却产生：

```json
{
  "path": "src/app.py",
  "start_line": "10"
}
```

字符串 `"10"` 看起来可以转换成整数 `10`，但自动转换会隐藏 Agent 没有遵守 Schema 的事实，也可能让不同输入在进入 Runtime 后变成相同值。对于路径、布尔值、枚举和标识符等字段，宽松转换还可能产生更难察觉的歧义。

候选方案：A 允许 Pydantic 的默认类型转换，只要能转换就接受；B 在 AgentDecision 与工具 arguments 的 Runtime 边界启用严格类型校验，类型不符时返回 INVALID_TYPE，并让 Agent 生成新的合法 Decision。当前推荐 B，使实际接收的数据与公开契约一致。

严格校验不等于所有业务规则都由类型系统完成。正数、最大超时、项目相对路径、old_text 唯一匹配等仍需要字段约束或 Runtime 业务检查；类型正确只是进入下一层检查的条件。

用户选择方案 B，并正确说明开启 Pydantic 严格校验后要求输入数据类型符合契约，类型不符时返回错误。该设计决定确认。补充边界：Pydantic 先产生 ValidationError，Runtime 再将其转换为 ForgeMind 稳定的 SchemaValidationError，例如 code=INVALID_TYPE；Agent 不直接依赖第三方库的原始错误文本。

## 38. 三层校验边界（教学草案）

Runtime 接受 ToolCallDecision 时，不应把所有检查都塞进 Pydantic，也不能只检查 Python 类型。第一版按信息依赖分成三层：

1. 结构与类型校验：由 Pydantic 检查必填字段、未知字段、严格类型、枚举和联合类型分支。失败时 Tool 不执行，也不生成 AcceptedAction/action_id。
2. 字段值约束：检查只依赖当前输入值的规则，例如 start_line >= 1、timeout_seconds > 0、path 非空、列表至少一项。这类规则可以由 Pydantic 字段约束或模型校验表达。失败时仍属于 Decision Schema 未通过，不生成 AcceptedAction/action_id。
3. Runtime / Tool 事实检查：前两层通过后，Runtime 生成 AcceptedAction/action_id，再检查必须访问当前项目或执行环境才能知道的事实，例如路径解析后是否仍在项目内、expected_version 是否匹配、old_text 是否唯一、命令是否获授权。不能把这些动态事实伪装成纯 Schema 校验。

例如 start_line=-5 的类型是整数，因此通过第一层，但违反第二层的取值范围；path="src/app.py" 是否存在不能只看字符串，需要读取当前工作区事实。

前两层失败返回统一 SchemaValidationError，并可写入独立 attempt 审计记录，但不伪造成带 action_id 的执行 Observation。第三层若由 Runtime 的执行前检查发现不满足，返回 status=rejected 的 Observation，并关联已经生成的 action_id；若 Runtime 已调用 Tool，Tool 在实际读取时发现文件不存在，则按既有协议返回 status=failed 的 Observation。具体由 Runtime 还是 Tool 拥有某项事实检查，需要在实现适配器时保持唯一责任并用测试固定，不能重复检查后返回互相矛盾的状态。

顺序如下：

```text
AgentDecision
  → 第一层：结构与类型
  → 第二层：字段值约束
  → Runtime 生成 AcceptedAction / action_id
  → 第三层：权限、版本和环境事实
  → Tool
```

用户正确把三个例子依次归入第一、第二、第三层。第三项称为“版本类型”不准确，已纠正为当前文件版本事实或执行前置条件不匹配；层级判断本身正确。

用户进一步正确回答：第一种 Schema 类型错误尚无 action_id；第二种 expected_version 不匹配和第三种 Tool 读取文件不存在已有 action_id。第二种发生在 Tool 前，Observation.status=rejected；第三种发生在 Tool 调用后，Observation.status=failed。该题通过。

## 39. 缺省参数与 AcceptedAction 规范化（教学草案）

ReadFileArguments 已确认 start_line 和 max_lines 可以省略：start_line 缺省为 1，max_lines 缺省为系统受控分段大小。但“调用者可以省略”不等于“执行记录也应该继续省略”。

候选方案：

- A：AcceptedAction 仍不保存 max_lines，由 Tool 执行时自行决定默认值；
- B：Runtime 在接受 Decision 时解析缺省值，把实际采用的 start_line 和 max_lines 写入 AcceptedAction.arguments，再交给 Tool。

当前推荐 B。AcceptedAction 是可执行、可审计的权威记录，应完整表达 Tool 实际收到的有效参数。如果默认值只隐藏在 Tool 内，之后修改系统默认配置时，历史 Action 无法单独说明当时执行了多少行，也不利于重放与解释结果。

具体 DEFAULT_READ_LINES 和 MAX_READ_LINES 数值仍需通过大文件、长单行及上下文预算测试确定，在测试前不凭空写死。第一实现切片将先建立严格基础模型和 ReadFileArguments；数值常量确认后再把它变成可执行代码。

用户选择方案 B，并说明这样看到的信息更全面明确，方案 A 缺少实际默认参数记录。该设计决定确认：Runtime 把缺省值规范化后写入 AcceptedAction.arguments，Tool 接收明确的有效参数。

## 41. read_file 的双重输出限制（教学草案）

用户正确指出一行可以包含很多数据，例如很长的代码或注释。因此 max_lines 只能限制行数，不能可靠限制返回内容的字节数或进入 Agent 上下文后的大小。该题通过。

MVP 的 read_file 需要同时受两种限制：

- 行数限制：由请求的 max_lines 与系统 MAX_READ_LINES 上限共同决定；
- 字节限制：由 Runtime/Tool 的 MAX_READ_BYTES 硬上限控制，防止少数超长行产生过大 Observation。

字节数和模型 token 数不是同一单位，但字节上限可以在不调用特定 tokenizer 的情况下提供确定性资源保护。后续上下文整理层仍需根据模型预算形成摘要或选择片段，不能把 MAX_READ_BYTES 当作完整 token 预算。

AgentDecision 不应自行提高系统硬上限。Runtime 创建 AcceptedAction 时，需要记录本次实际采用的有效行数限制及系统字节限制，保证执行记录能解释结果为何截断。具体字段放入规范化 arguments、独立 execution_limits 或策略引用，需与 AcceptedAction 总体结构一起收束。

尚待确认的边界是：如果单独一行已经超过 MAX_READ_BYTES，MVP 应返回半行片段，还是拒绝并明确报告超长行。返回半行可取得部分内容，但容易让 Agent 把不完整代码当成完整行；拒绝更明确，但需要未来增加按字符/字节范围读取能力才能处理压缩文件或超长生成内容。

用户选择拒绝超长单行并返回明确事实，理由是避免捏造完整内容、减少 Agent 猜测；后续优化应增加或调整明确的读取范围参数。该设计决定确认。MVP 返回 LINE_TOO_LARGE，并报告可安全公开的行号、实际大小和限制，不把半行放入普通成功结果。未来增加字符/字节范围读取时需使用新的显式契约。

## 45. AcceptedAction 的不可变性（教学草案）

AcceptedAction 是 Runtime 已接受的权威执行记录。它创建后若允许原地修改，例如把 arguments.max_lines 从 200 改为 1000，原 action_id 就会在不产生新记录的情况下代表另一个操作，Observation、授权和审计均可能关联到错误内容。

候选方案：A 允许修改原 AcceptedAction；B AcceptedAction 及其嵌套 arguments 均不可变，内容变化必须形成新的 Decision，并由 Runtime 分配新的 action_id。当前推荐 B，使一个 action_id 始终对应一份稳定请求。

只冻结 AcceptedAction 最外层仍不够：如果 arguments 对象可变，代码仍可通过 accepted.arguments.max_lines=1000 修改内部内容。因此实现需要保证嵌套数据契约也不可原地改写，或在 AcceptedAction 中使用不可变副本。首版倾向让已校验契约模型统一不可变，状态变化通过新记录表达。

用户选择方案 B，正确指出若允许原地修改，已经通过校验的 Action 可能被改成 max_lines=10000 等违规内容，方案 B 更保守且强制新内容再次经过 Runtime 审核。该设计决定确认。

## 48. next_action_id 依赖注入讲解

用户对为何传入 next_action_id 而不在接受函数中写死 uuid4 回答不清楚。本点记为待讲解，不算独立掌握。

若 accept_read_file_decision 内部直接调用 uuid4，它会同时承担“Decision 转换”和“选择 ID 生成方案”两个职责。测试无法直接指定预期编号；未来切换数据库序列、分布式 ID 或可恢复计数器时也必须修改接受函数。

把 next_action_id 作为参数传入后，接受函数只负责转换；调用方负责选择生成器。测试传入固定函数得到 action-001，正式 Runtime 可传入 UUID/数据库实现，故障测试还可传入会抛错或返回冲突值的生成器。这种把外部能力通过参数交给核心逻辑的方式称为依赖注入。

依赖注入本身不保证 ID 唯一，只让职责可替换、可测试。唯一性仍由所注入的生成器及 State/持久化约束共同保证。

用户回答将来更换数据库编号生成器不需要修改接受函数，核心理解正确。代码示例中写成传入 uuid4()，已纠正：next_action_id 需要的是稍后可调用的函数，应传 uuid4 或包装后的生成器；uuid4() 是立即执行后的 UUID 结果，不符合 Callable[[], str]，并且返回类型也不是约定的字符串。该点记为概念理解、Python 调用语法经纠正。

重试具有 max_id_attempts 上限，默认 3。测试覆盖第一次 action-001 冲突、第二次 action-002 成功，以及生成器连续返回 action-001 时达到上限抛出 ActionIdAllocationError。有限重试防止错误生成器造成无限循环。

当前注册表只适用于单进程内存教学/MVP 切片，不具备进程重启恢复、跨进程并发或数据库唯一约束，不能视为最终持久化 State。后续替换存储实现时仍需保持“重复拒绝、绝不覆盖”的契约。

用户正确回答权限拒绝后不应删除 AcceptedAction，而应追加 status=rejected 的 Observation；删除会丢失必要执行步骤和拒绝依据。该题通过。

## 51. RejectedObservation 与 State 关联第一实现切片

新增 ObservationErrorCode、ObservationError、ObservationErrorDetail 和 RejectedObservation。权限拒绝使用稳定码 PERMISSION_DENIED；status 通过 Literal 固定为 rejected；该变体只有 error，没有 result，额外成功结果会被 StrictContractModel 拒绝。

错误 details 使用不可变 tuple，而不是 list，避免 frozen 外层模型内部仍可追加或删除详情。当前详情键和值均为字符串；后续若需要更复杂结构，必须继续保持可序列化和不可变边界。

新增 InMemoryObservationRegistry。record 写入前先确认 Action 已注册，未知引用转换为 UnknownActionIdError；同一 Action 已有终态 Observation 时抛出 DuplicateObservationError，并保留首次记录。测试确认追加 rejected Observation 后原 AcceptedAction 仍存在，二者通过 action_id 关联。

当前 V0.1 规定每个 Action 只有一个终态 Observation。若未来需要记录执行中的多个事件，应新增独立事件流模型，不能用后续终态结果覆盖前一条事实。与 Action 注册表相同，当前 Observation 注册表仅为单进程内存切片，不具备持久化或并发事务保证。

用户对权限拒绝 Observation 应由谁创建回答不清楚。已讲解：PERMISSION_DENIED 表示权限检查真实发生并阻止 Tool，属于 Runtime 的权威执行事实；Agent 只能提出 Action 或预测需要授权，不能自行写入拒绝结果。本点记为经讲解，不算独立掌握。

## 52. Runtime 权限拒绝入口第一实现切片

新增 `record_permission_rejection`，由 Runtime 在 Tool 尚未执行、权限检查已经拒绝后调用。它接收已登记的 `AcceptedReadFileToolAction`，创建使用同一 `action_id` 的 `RejectedObservation`，错误码固定为 `PERMISSION_DENIED`。

该入口先调用 `InMemoryObservationRegistry.record`，成功写入 State 后才返回 Observation。这样 Agent 收到的拒绝结果必然已经成为下一轮可以查询的权威历史；若 State 拒绝未知 action_id 或重复终态，异常会继续向上报告，Runtime 不会伪装成已经记录成功。

本切片只记录已经得到的权限拒绝事实，尚未实现权限范围匹配、向用户发起授权询问及用户授权决定的数据结构。它也不调用 `read_file`，因此状态是 `rejected`，不是 `failed`。

测试按照“已登记 Action → Runtime 记录权限拒绝 → Action 仍保留 → Observation 可按 action_id 查询”的完整链路编写。目标测试先因权限模块不存在而失败，实现最小入口后通过。

## 53. PermissionCheckResult 第一实现切片

权限检查不能只返回 `allowed: bool`。`false` 无法区分“当前没有足够授权、需要询问用户”和“用户或安全规则已经明确拒绝”，会造成重复询问、错误终止或越权执行。第一版 `PermissionCheckOutcome` 因此定义三个互斥值：`allowed`、`confirmation_required`、`denied`。

新增 `PermissionCheckResult`，包含 `action_id`、稳定枚举 `outcome`、非空解释 `reason` 和至少一项 `basis_ids`。程序分支只依据枚举，不解析自然语言 reason；basis_ids 引用权限记录或安全策略，使结论可以追溯。依据使用不可变 tuple，且其中每个编号均不可为空。

PermissionCheckResult 仍是 Runtime 内部的检查结论，不等于最终 Observation。`denied` 经过 Runtime 处理后可形成 `status=rejected` 的 RejectedObservation；`confirmation_required` 应创建待确认记录并使任务进入等待，而不能提前写成权限拒绝；`allowed` 只表示可以进入后续安全、版本和环境检查，不代表 Tool 已执行成功。

本切片暂不实现路径范围匹配。当前 Action 路径尚未经过 Runtime 的项目根目录解析与规范化，直接比较 `src/a.py`、`./src/a.py` 等字符串可能错误地允许或拒绝操作。目标测试先因 permissions Schema 模块不存在而失败，最小实现后 5 项通过。

用户正确回答：Runtime 没找到已有授权、也没有找到用户拒绝记录时，应当“待问用户”，对应 `confirmation_required`。它不能写成 denied，也不能提前生成 RejectedObservation；该题通过。

## 54. denied 权限结论转换为 rejected Observation

`record_permission_rejection` 改为接收完整 `PermissionCheckResult`，不再接收一条脱离来源的 message。Runtime 首先确认 permission_check.action_id 与当前 AcceptedAction.action_id 完全相同，再确认 outcome 确实是 denied。任何一项不满足都抛出明确异常，并且不写入 ObservationRegistry。

转换成功时，Observation 的 message 使用检查结果的 reason，所有 basis_ids 转换为 `permission_basis_id` 错误详情。这样 Agent 收到拒绝事实时仍能知道 Runtime 根据哪些权限决定或安全策略作出判断，而不是只看到无法追溯的文字说明。

测试覆盖正确转换、Action 引用不一致、allowed 被误转为 rejected、confirmation_required 被误转为 rejected。首次实现后，三项测试的业务异常均已正确触发，但测试错误地假定 ObservationRegistry.get 在缺少记录时返回 None；实际契约是抛出 KeyError。依据真实接口修正断言后，定向测试 4 项通过，没有为了迎合错误测试而改变注册表行为。

用户正确回答：permission_check 属于 action-002 时，不能写入 action-001，必须根据 ID 确认关联标识。该题通过。

## 55. PendingReadFilePermissionRequest 第一实现切片

`confirmation_required` 不生成 RejectedObservation，而是形成等待用户回答的权限请求。新增 `PendingReadFilePermissionRequest`，保存 permission_request_id、task_id、action_id、固定 status=pending、固定 read_file 路由标签、完整 ReadFileArguments、reason 和 basis_ids。

action_id 标识待执行的 Action，permission_request_id 标识本次权限询问，二者不能混用。用户之后的决定需要引用具体 pending request，Runtime 再核对它所关联的 Action，防止一条脱离上下文的“同意”被应用到另一项操作。

请求保存完整 arguments 快照，而非只保存 path。读取起始行、最大行数和 expected_version 都可能影响用户实际批准的范围；若确认后参数变化，应重新检查并建立新请求，不能扩大原授权。

pending 记录不可原地修改为 approved/rejected。用户回答将形成独立 PermissionDecisionRecord，保留原始询问与原始回答的关联历史。目标测试先因 Schema 类不存在而失败；实现后 5 项通过。当前尚未实现 Runtime 转换入口、请求注册表或任务 WAITING_USER 状态。

用户回答保存完整参数可以防止读取过多信息并帮助处理范围越界，核心判断正确。补充：pending 记录本身不访问文件，不能独立判断起始行是否超过实际 EOF；它保存用户批准的读取范围供后续检查。expected_version 还防止确认后文件已变化却沿用旧授权。该题通过并补充边界。

## 56. Pending 权限请求创建与登记入口

新增 `create_and_register_pending_read_file_permission_request`。入口只接受 action_id 与当前 AcceptedAction 一致、outcome 为 confirmation_required 的 PermissionCheckResult；allowed 和 denied 分别属于继续执行与拒绝分支，不能创建用户询问。

入口通过注入的 next_permission_request_id 生成询问编号，从不可变 AcceptedAction 复制 task_id、路由和完整 arguments，从 PermissionCheckResult 复制 reason 与 basis_ids。创建后先登记到 State，再返回给上层；登记失败时不能向用户展示一条 State 中不存在的临时询问，也不能进入 WAITING_USER。

新增 `InMemoryPermissionRequestRegistry`。它确认关联 Action 已登记，并将 pending 的 task_id、action_type、tool_name 和完整 arguments 与权威 Action 再次比较。即使 action_id 相同，改变文件路径或读取范围的请求仍被视为快照不一致并拒绝。重复 permission_request_id 也明确失败且不覆盖原询问。

目标测试覆盖正确创建登记、action_id 不一致、allowed/denied 误入确认分支、重复询问编号、未知 Action 和操作快照变化，共 7 项通过。当前注册表仍为单进程内存实现，且尚未建立任务 progress=WAITING_USER 或 PermissionDecisionRecord。

用户正确回答：没有 permission_request_id 的“同意”不能直接应用，因为可能同时存在多个待确认 Action，不同请求对应的 approve/reject 可能被错误关联。该题通过。

## 57. PermissionDecisionRecord 第一实现切片

新增 `PermissionDecision`，只包含用户对具体 pending 请求作出的 `approve` 和 `reject`。它不同于 PermissionCheckOutcome 的 allowed/confirmation_required/denied，也不同于 pending 请求的 status；三个枚举分别描述检查结论、询问状态和用户决定，不能混用。

新增不可变 `PermissionDecisionRecord`，包含 permission_decision_id、permission_request_id、task_id、action_id、decision、固定 source=user 和 raw_response。程序根据稳定 decision 枚举分支；用户原话独立保存，不能被归一化结果覆盖。

raw_response 用于保留附带条件。例如用户回答“同意，但只读取前 20 行”，若系统误归一化为对原 200 行请求的完整 approve，原话能暴露解释冲突。Schema 只保证结构完整，尚不能证明归一化结果忠实表达原话，带条件的回答后续可能需要拒绝直接批准并创建范围更小的新 Action/询问。

source 固定为 user，Agent 的预测或建议不能伪装成授权。授权范围不在决定记录中重复复制，而由它引用的不可变 pending request 提供，避免两份范围字段发生冲突。目标测试先因决定类型不存在而失败；实现后相关文件 14 项通过，其中本节新增 9 项。

当前记录尚未写入 State。下一步需验证 pending request 存在、task_id/action_id 完全匹配、同一请求没有已有决定，以及 permission_decision_id 不重复。

用户回答 raw_response 用于让 State 保持完整上下文，判断正确。补充：它还使系统能对照用户原话与归一化 decision，发现“同意，但只读取前 20 行”等条件被错误丢失。该题通过。

## 58. PermissionDecision State 登记第一实现切片

新增 `InMemoryPermissionDecisionRegistry`。record 首先按 permission_request_id 查找原始 pending request；找不到时拒绝孤立决定。找到后继续核对 task_id 和 action_id，防止调用方把同一回答重新标记后应用到另一任务或 Action。

注册表同时维护 permission_decision_id 索引和 permission_request_id 索引。前者保证决定编号唯一且不覆盖；后者规定一个 pending request 在 V0.1 只有一个最终用户决定，禁止先记录 approve 后再用 reject 覆盖原事实。

所有校验完成后才同时写入两个索引，失败时不留下半条状态。若用户后续改变决定，需要设计新的撤销/替代记录或重新发起确认，不能原地改写历史。本切片尚未实现这种变更流程。

目标测试先因决定注册表模块不存在而失败；实现后 6 项通过，覆盖成功登记、未知请求、task/action 错配、重复决定编号和同一请求的第二个决定。当前仍是单进程内存实现，也尚未将 approve/reject 分别连接到继续执行和 RejectedObservation。

## 59. 已登记权限决定的后续分支

新增 `resolve_registered_permission_decision`。Runtime 只接收 permission_decision_id，并从 `InMemoryPermissionDecisionRegistry` 读取已经写入 State 的权威决定；未登记的临时“同意”或“拒绝”不能进入执行链路。解析后再按决定中的 action_id 从 InMemoryActionRegistry 取得原始 AcceptedAction。

approve 被转换为 outcome=allowed，reject 被转换为 outcome=denied；两者的 basis_ids 都引用原 permission_decision_id。reject 结果继续交给既有 `record_permission_rejection`，形成并登记 rejected Observation。approve 只恢复原 Action 的后续版本、安全和环境检查，本步骤不调用 Tool，也不生成成功 Observation。

目标测试覆盖 approve、reject、未知决定编号，以及 reject 决定到 rejected Observation 的完整链路。

用户正确回答批准后不能增大 max_lines，因为它是用户确认的固定值。参数变化代表另一项操作，必须形成新 Action 并重新检查权限；该题通过。

## 60. 权限批准后恢复权威 Action

`resolve_registered_permission_decision` 现在同时返回 ActionRegistry 中的权威 AcceptedReadFileToolAction 和新的 PermissionCheckResult。后续流程直接使用该不可变 Action，不能由调用方另传一份使用相同 action_id、但 max_lines/path 等参数已经变化的副本。

approve 只生成 outcome=allowed，随后仍须检查文件版本、安全条件和环境事实；本步骤不调用 Tool，也不创建成功 Observation。reject 生成 denied，并通过现有 record_permission_rejection 形成可追溯的 rejected Observation。

实现前重新检查工作区时发现第 59 节的决定解析已存在，因此没有新增同义函数，而是增强现有入口。定向测试现在覆盖取回同一权威 Action 且 max_lines 保持 50、reject 完整链路以及未登记决定，共 3 项通过。

用户正确回答：批准版本为 v1、执行前实际版本变为 v2 时不能继续，Runtime 必须确认版本相同才可通过。该题通过。

## 61. 批准后的 read_file 版本门禁

普通 ReadFileArguments 仍允许 expected_version=None；但 PendingReadFilePermissionRequest 新增跨字段校验，进入用户确认流程的读取必须绑定非空 expected_version。不能把“未绑定版本”解释成用户批准任意未来内容。

新增 `verify_approved_read_file_version`。它接收已经恢复的权威 AcceptedReadFileToolAction 和可信来源提供的 actual_version。两者相同则返回同一 Action；缺少 expected_version 时抛出 ReadFileExpectedVersionRequiredError；版本不同时抛出 ReadFileVersionMismatchError，并保留 action_id、expected_version 和 actual_version。

本门禁不修改 Action，也不自动把新版本视为已授权。版本变化后应重新获取必要上下文，根据新版本形成新的 Action，并重新检查权限。实际版本如何计算将在 read_file Tool 实现时确定，不能用时间戳或猜测值冒充内容版本。

Runtime 检查与 Tool 真正读取之间仍有竞争窗口，因此 Tool 在实际打开/读取文件时还必须原子地或尽可能贴近使用点再次验证 expected_version。本切片只完成 Runtime 门禁，不声称已经消除该竞争条件。

目标测试先分别证明 pending Schema 错误接受无版本请求，以及 versioning 模块不存在；实现后 4 项新增要求通过。完整测试首次运行有 10 个旧夹具因未绑定版本而失败，逐项为原本测试其他行为的有效 pending 数据补充明确版本后，完整测试 77 项通过。

用户对 Runtime 检查通过后 Tool 是否还能跳过版本校验回答不知道。已讲解检查与使用之间的竞争（TOCTOU）：Runtime 检查 v1 后，文件可在 Tool 打开前变成 v2；若 Tool 不复检，就会返回用户未批准的内容。本点记为经讲解，不算独立掌握。

## 62. read_file 使用点的同一快照版本校验

新增 `calculate_content_version`，对文件完整原始 bytes 计算 SHA-256，并返回 `sha256:<hex>`。版本基于原始字节，不对编码、换行或非法字节做隐式规范化，否则不同的实际文件内容可能被错误视为同一版本。

新增 `verify_read_file_snapshot_version`。Tool 将实际读取到、准备返回的同一份 bytes 传入；函数计算 actual_version 并复用 `verify_approved_read_file_version` 与 Action 的 expected_version 比较。匹配时返回实际版本，不匹配或缺少期望版本时抛出既有明确错误。

版本通过后，Tool 必须继续从同一个 content 对象解码、分行和截取，不能重新打开文件取得第二份内容。这样校验对象与返回对象来自同一字节快照，避免在验证后重新读取而重新引入 TOCTOU 窗口。

本切片尚未实现真实路径打开、编码处理、行范围返回或 Observation 转换，只建立 Tool 使用点可复用的版本核心。新增 3 项测试先因函数不存在而失败，实现后版本测试文件共 6 项通过。

用户正确回答：验证第一份字节后重新打开并返回第二份内容不安全，第二份可能已经变化；若是敏感文件会造成未经批准的内容泄漏。核心规则是“校验哪份字节，就只能从哪份字节生成结果”。该题通过。

## 63. Runtime 版本冲突的 rejected Observation

ObservationErrorCode 新增 VERSION_MISMATCH。新增 `record_read_file_version_rejection`，用于 Runtime 在调用 Tool 前的版本门禁发现 expected_version 与 actual_version 不一致时，创建并登记 RejectedObservation。

记录入口先确认 ReadFileVersionMismatchError.action_id 与当前 AcceptedAction.action_id 一致，防止把另一行动的版本比较结果挂到当前 Action。成功记录保留 expected_version 和 actual_version 两项结构化详情，Agent 可依据真实差异重新获取上下文，而不是猜测失败原因。

该路径 status=rejected，因为冲突在 Runtime 调用 Tool 前发现，Tool 未执行。若 Tool 已被调用，并在实际字节快照检查中发现版本变化，顶层状态应为 failed；后者需要单独的 FailedObservation，不能复用本入口伪装成执行前拒绝。

测试先因版本拒绝入口和关联错误类型不存在而失败；最小实现后 2 项通过，覆盖完整版本冲突记录以及禁止跨 Action 关联。

用户正确回答 Tool 已经读取字节后发现版本不一致应为 failed，因为 Tool 已执行。其“rejected 是读取不了”的说法补充修正为：rejected 的判断标准是 Tool 尚未被调用；若 Tool 已调用后遇到文件不存在、系统读取错误或版本冲突，同样属于 failed。核心答案正确，该题通过。

## 64. Tool 快照版本冲突的 FailedObservation

新增 `FailedObservation`，固定 status=failed，必须携带 error，严格模型拒绝额外成功 result。新增 TerminalObservation 联合类型，使 InMemoryObservationRegistry 可以保存 rejected 或 failed，同时继续执行“已登记 Action、每个 Action 只有一个终态、绝不覆盖”的规则。

新增 `record_read_file_snapshot_failure`。它用于 Tool 已读取实际 bytes、在同一快照版本校验中发现冲突的场景；入口核对 mismatch.action_id 后创建 failed Observation，并在返回前登记到 State。

Runtime 执行前冲突与 Tool 使用点冲突共用 VERSION_MISMATCH 及相同 expected/actual 结构化详情，通过 Observation.status 区分处理阶段。提取 `_version_mismatch_error` 复用错误转换，避免 rejected/failed 两条路径产生不同的详情格式。

目标测试先因 FailedObservation 和快照失败入口不存在而失败；实现后 3 项通过，覆盖 failed 记录、禁止成功 result 和禁止跨 Action 关联。真实 read_file Tool 尚未负责打开文件、调用快照校验和生成成功结果。

## 76. search_code V0.1 实现设计确认

用户在 Python 原生逐行搜索、ripgrep 子进程和 Python AST 语义搜索三种方案中选择方案 A：使用 Python 原生能力实现大小写敏感的普通文本搜索。该方案不依赖外部程序，行为便于理解和测试；未来可在保持 Schema 稳定的前提下替换或扩展内部搜索引擎。

V0.1 输入固定为 `query`、`scope` 和 `max_results`。query 是非空普通文本；scope 是项目内相对路径，默认 `.`，可以指向单个文件或目录；max_results 默认 20，取值 1～100，只限制返回条数，不表示项目总匹配数。

目录范围内只递归搜索 `.py` 文件，并忽略 `.git`、`.venv`、`__pycache__` 与 `.test-tmp`。scope 直接指向单个非 `.py` 文件时，Runtime 在调用 Tool 前以不支持的搜索目标拒绝，不能把“没有执行搜索”伪装成零匹配。每个候选文件在读取前仍须确认解析后位于项目根目录内，不能借符号链接越界。

候选文件按项目相对 POSIX 路径排序，同一文件内按行号升序返回，使相同快照和参数得到确定顺序。每个 match 保存项目相对路径、从 1 开始的行号和实际匹配行。V0.1 不提供正则、忽略大小写、AST 符号关系或可配置文件类型。

每个候选文件最多读取 64 KiB，并以 UTF-8 解码。文件超限、无法读取、无法解码或解析后越出项目根目录时跳过该候选，并以 `FILE_SKIPPED` 表明结果不完整；不能为了完成一次搜索而无界读取整个项目。

结果继续使用 `returned_count` 和 `is_complete` 区分“实际返回多少”与“是否完整覆盖”。搜索发现第 `max_results + 1` 条匹配或跳过无法读取的候选文件时，is_complete=false，并提供稳定的 incomplete_reasons；恰好只有 max_results 条且全部候选均已扫描时仍可为 true。完整搜索后零匹配仍属于 success。

实现按小切片推进：先完成 SearchCodeArguments，再完成 match/result Schema、安全范围解析、受限逐行搜索、Observation 登记和统一 Runtime 执行入口。每个切片先建立失败测试，并保留核心代码由用户实现。

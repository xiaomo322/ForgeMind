# ADR-0001：使用 SQLite 持久化任务事实

## 状态

已接受

## 日期

2026-09-27

## 背景

ForgeMind 已经用四个内存 Registry 保存 Action、权限请求、用户决定和 Observation。它们能保证单进程内的唯一 ID、引用关系和不可覆盖规则，但程序退出后所有事实都会消失。等待用户确认或执行中断后，Runtime 因此无法恢复原任务。

持久化层必须满足：

- 每条已登记事实在函数返回前可靠写入；
- 同一 ID 不能覆盖原记录；
- 权限和 Observation 必须继续引用已存在的 Action；
- 进程重启后使用严格 Schema 重建对象；
- MVP 不要求独立数据库服务或多主机扩展。

## 决策

V0.1 使用 Python 标准库 `sqlite3` 和单个项目级 SQLite 数据库。结构化对象使用 Pydantic JSON 保存，同时把 ID、任务 ID 和类型保存为可约束、可查询的列。

先逐步实现 Action、权限请求、用户决定和 Observation 的持久化 Registry，最后用重启恢复测试验证完整链路。数据库写入使用事务和唯一键；严格模型校验仍是读取持久化数据的最后边界。

## 考虑过的替代方案

### 结束时导出一个 JSON 文件

容易理解，但进程在导出前崩溃会丢失新事实；重写整个文件也难以保证多个关联记录的一致性，因此不采用。

### 追加 JSONL 事件

保留历史且易于检查，但需要自行处理半行写入、唯一 ID、引用完整性、并发锁和压缩。当前阶段会把重点从 Agent State 转移到存储引擎细节，因此不采用。

### 外部数据库服务

PostgreSQL 等系统能支持更强并发和多实例部署，但 MVP 是本地单用户 Agent，引入服务、迁移和部署成本过高，因此暂不采用。

## 后果

- 无需新增第三方依赖，项目可继续本地运行；
- SQLite 事务和约束负责磁盘层的一致性；
- JSON payload 仍必须通过当前严格 Pydantic 联合类型验证；
- 从磁盘恢复的对象与原对象值相等，但不会保持 Python 对象身份；
- SQLite 适合当前单机 MVP，未来多主机并发需求出现时需要新的 ADR。

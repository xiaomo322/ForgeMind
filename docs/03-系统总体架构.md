# ForgeMind 系统总体架构

**版本：V0.1**  
**状态：设计中；Tool 调用路径已确认，总体架构尚未定稿**

## 1. 总体关系（第一版整合图）

```text
用户提交任务 / 回答确认
           ↓
Runtime：循环控制、Action 校验、权限与安全检查
  ├─ 提供 State 上下文 → 调用 Agent → 接收 Action
  ├─ 检查通过 → 调用 Tool → 操作项目工作区
  ├─ 接收工具实际结果 → 整理 Observation → 更新客观 State
  └─ 继续下一轮 / 暂停等待 / 结束并交付报告
```

Tool 执行后产生 Observation，由 Runtime 整理客观执行结果并更新 State，Agent 再读取 State 决定下一步。

图中 Runtime 调用 Agent 表达程序控制关系；Agent → Action → Runtime → Tool 表达操作请求路径，两者不矛盾。权限与安全检查是 Runtime 的必经职责，是否拆分独立代码模块后续确定。用户交互的 CLI 或 Web 形式尚未确定。

## 2. 模块职责

| 模块 | 职责 |
|---|---|
| Agent | 理解、分析、规划、决策、判断 |
| State | 保存任务循环所需的当前上下文 |
| Runtime | 校验 Action、执行权限与安全检查、调度 Tool、整理结果 |
| Permission / Safety | 在执行前进行最终拦截 |
| Tools | 读取、搜索、修改、运行 |
| 项目工作区 | 被操作的用户项目 |

## 3. 关键边界

- Runtime 不猜测 Agent 意图；
- Runtime 不调用 LLM 补全缺失参数；
- Action 参数不完整时返回明确错误；
- Agent 与 Runtime 之间使用严格结构化协议；
- Agent 的判断不能替代 Runtime 的安全检查。

## 4. 第一阶段范围

第一阶段只建立完成简单 Python Bug 修复闭环所需的最小架构，不预先设计 RAG、Memory、Multi-Agent 或部署系统。


## 5. 已确认决策：所有 Tool 操作统一经过 Runtime

确认日期：2026-09-12。用户在讨论 C 方案的检查遗漏风险后，选择 B。

调用路径：Agent → Runtime → Tool。

Agent 生成操作请求，Runtime 校验参数、权限和风险，通过后才调用 Tool。Agent 不得拥有绕过 Runtime 直接执行 Tool 的通道。

原因：安全检查必须成为统一的必经入口。如果由各个 Tool 自行请求 Runtime 检查，新增工具时漏写检查就可能绕过约束。该要求适用于所有 Tool，而不只是高风险工具；具体风险仍结合操作对象和范围判断。

## 7. State 与执行结果的连接（2026-09-12 课堂确认）

Tool 执行并返回实际结果；Runtime 按确定性规则将客观执行结果记录到 State；Agent 读取 State，分析原因并决定下一步 Action。

```text
Agent 读取 State → 生成 Action → Runtime 校验并调用 Tool
                                      ↓
                              Tool 返回实际结果
                                      ↓
                           Runtime 更新客观 State
                                      ↓
                             Agent 读取并继续决策
```

Action 表达请求做什么，Observation 表达本次操作返回什么，State 保存当前任务积累的上下文。State 不只是日志，也是下一轮决策的依据。

测试结果必须区分：

- 测试运行后有用例失败：记录实际通过、失败情况及失败详情。
- 测试未能启动，例如找不到 pytest：记录测试未能运行及具体原因，不能记成测试用例失败，也不能声称测试通过。

用户已正确说明：测试未能运行时，应把真实运行情况及原因提供给 Agent。Agent 根据实际结果判断继续定位、补充信息或请求用户参与，不能只凭“应该修好了”改变客观记录。

本节仅明确客观执行结果的记录职责，不代表 State 的所有内容均由 Runtime 独立决定。Agent 对原因的推测不能直接作为已确认事实；其具体维护方式和字段结构留待后续讨论。

## 8. 客观事实与原因推测（课堂记录）

测试实际返回 100 元、预期 80 元，是该次测试已观察到的事实；“计算函数没有使用折扣参数”只是原因推测，不能仅凭错误结果确认原因。

课堂展示函数 `return price * discount` 后，用户不再认定函数未使用折扣参数，并提出检查 discount 的实际传入值。这说明下一步调查应随证据调整，而不是按最初猜测直接修改代码。

该示例只用于教学，不是项目中实际运行的测试。检查输入值是下一步验证动作，并不意味着已经确认输入错误。读取调用代码与观察实际运行值提供的证据也应分别记录。

已讲解：新证据否定旧推测时，应保留其被否定的判断及依据，避免再次作为有效线索。Agent 负责提出或修正推测，具体写入接口与校验方式后续设计；Runtime 不负责推断业务错误原因。该原理已讲解，未另行考核，尚未确定具体状态字段或更新协议。

## 9. 循环驱动、暂停与恢复（课堂归档）

Runtime 中的确定性循环控制逻辑负责调用 Agent、处理请求、保存结果并安排下一轮；Agent 负责决定下一步做什么。循环控制器不是另一个 Agent，具体文件组织尚未确定。

需要用户授权时，保存当前任务、证据、待执行操作及确认原因，暂停工具执行并等待回答，不反复调用 Agent。授权对应具体操作及范围，不视为永久授权。

- 用户同意：核对授权，并重新检查操作的执行条件；仍满足条件才执行。
- 用户拒绝：不执行该操作，记录拒绝结果，交给 Agent 评估其他方案。
- 用户取消任务：结束本次运行。

用户已正确回答：等待期间手动修改文件后，必须先检查文件是否仍符合原修改条件。检查的目的在于确认方案仍适用，不是由 Runtime 自动重新设计修改方案。相关条件发生变化时，返回变化情况，由 Agent 重新评估；修改了授权对象或范围的操作不得直接沿用原授权。

等待确认是暂停，不是任务完成。循环还需要取消、完成与步数上限等控制出口；具体限制值和完成校验机制留待后续设计。

## 10. Bug 修复闭环与验证边界

教学流程：记录用户任务 → Agent 搜索并读取相关代码 → 依据证据定位 → 提出具体修改 → Runtime 检查并在必要时暂停确认 → Tool 修改 → 执行相关测试及必要的程序验证 → Agent 对照任务目标判断结果并报告。

Action 是请求，Observation 是一次操作的结果，State 是贯穿任务的上下文。修改工具成功只证明指定修改完成，不证明行为正确；测试通过只支持已覆盖场景，不能代替全部需求验收。价格函数测试通过但调用方传错折扣时，用户问题仍可能存在。

# ForgeMind Tool 工具协议

**版本：V0.1**  
**状态：初步确定**

## 1. 工具职责

Tool 只负责执行明确、结构化的操作。Tool 不负责理解“帮我修复登录功能”这类自然语言任务，也不自行决定修改方案。

## 2. MVP 工具

| Tool | 职责 | 风险 |
|---|---|---|
| `read_file` | 读取指定任务相关文件 | 低 |
| `search_code` | 搜索文件、函数、类或文本 | 低 |
| `edit_file` | 按 Agent 指定内容修改文件 | 中 |
| `run_command` | 执行 Agent 指定的程序或命令 | 按命令判断 |
| `run_tests` | 执行相关测试 | 低到中 |

## 3. Tool Schema 要求

每个 Tool 后续必须明确规定：名称和用途、输入参数及类型、返回值、参数缺失和执行失败情况、权限要求与风险等级。

## 4. 调用规则

```text
Agent 生成 Action
  ↓
Runtime 校验结构和参数
  ↓
权限与安全检查
  ↓
Tool 执行
  ↓
返回 Observation
```

Runtime 不猜测意图、不自动补全参数。参数不完整时直接返回明确错误，由 Agent 重新决策。

## 5. 修改边界

`edit_file` 不应默认允许任意文件、任意范围修改。目标路径、修改范围和修改内容必须明确，并经过 Runtime 权限与安全检查。

具体参数格式仍待下一阶段正式定稿。

## 6. read_file 第一版契约草案（2026-09-13 教学中）

本节提出待用户讨论的最小方案，不视为最终 Schema 或已实现能力。

- 用途：读取项目内一个明确指定的文本文件，返回原始文本，不自行搜索、分析或修改。
- 输入草案：path 为必填字符串，表示相对于本次任务项目根目录的路径。根目录由任务配置提供，不由模型任意指定；编码首版候选为 UTF-8。
- 成功结果：返回目标路径与文本内容，空文件可以成功返回空字符串。
- 参数缺失或类型不符：Runtime 校验拒绝，不调用工具。
- 超出授权范围或敏感目标不被允许：Runtime 拦截，工具未执行。路径边界应按实际解析目标检查，具体实现后续设计。
- 执行错误：文件不存在、目标是目录、操作系统拒绝访问、无法按约定编码解码等，应明确区分，不用空字符串掩盖错误。
- 大文件处理：本节不定稿大小上限或分段参数；后续需明确，不能无提示截断后声称完整读取。

Tool 专用输入与返回内容，是外层 Action 和 Observation 的组成部分，不把整套任务 State 作为 read_file 的业务输入。工具是否被调用、请求关联和 Runtime 拦截情况由外层执行记录表达。

读取风险仍取决于对象、范围与敏感程度，表中低风险不是对所有文件的无条件授权。用户已正确指出：不存在却返回成功空内容会误导 Agent 认为文件存在，影响后续修改。该题通过。

## 7. 分段读取接口草案（教学讨论中）

用户提出大文件分批读取及摘要；已讲解 read_file 返回原文与范围，摘要由后续上下文整理处理，不能把未读部分概括为已知。用户尚未独立验证分段边界理解。

本节候选输入：path、start_line、max_lines。行号从 1 开始，max_lines 表示最多返回多少行而非终止行号；两项数值均为正整数。默认值、最大允许值及字符/字节限制后续确定，不把示例中的 100 当作既定限制。

候选输出：原文、实际起止行、实际返回行数、eof（本次读取是否到达末尾）。读第 101 行起最多 100 行，通常得到 101～200 行；若文件止于 160 行，则只返回 101～160 行及 eof=true。eof=true 不意味着前面的行已读过，也不证明整份文件已经完整读取。

State 保留本次实际范围。无需每次扫描全文件计算总行数；大文件优先搜索定位后读取相关范围。单行也可能很长，字节上限、超限反馈、空文件及起始行越界的具体输出另行讨论，当前不是可直接实现的完整协议。

用户已正确回答：返回 101～160 行且 eof=true 只能说明读到该段，不能证明全文读取；该题通过。

## 8. 空文件与越界（已讲解，边界协议待定）

空文件存在但无内容；文件不存在属于读取错误。起始行超出非空文件范围时，本次没有取得请求内容，不能当作空文件成功返回。

教学候选：空文件从初始位置读取可成功返回空内容、0 行、无实际行范围及 eof=true；非空文件起始行越界返回范围错误。空文件使用其他起始行等细节尚未定稿。

用户知道两者应区分，但将空文件误解为文件不存在；已通过新建空文本文件的例子纠正，不记为完全独立答对。

## 9. 分批读取的一致性（本节教学方案）

两批读取之间文件可能变化，行号相邻不代表两段来自同一份内容。例如先读旧文件第 1～100 行，随后开头插入 20 行，新文件第 101 行对应旧文件第 81 行，直接拼接会重复。

本节概念方案：返回与读取内容对应的版本标识，后续读取可携带预期版本；检测到不一致时明确反馈文件变化，不把不同版本的片段冒充同一版本全文。Runtime 记录版本与范围，Agent 决定重新搜索或读取相关内容。旧记录作为历史保留，不能继续视为当前版本证据。

版本标识是判断变化的信息，不要求使用 Git；具体采用内容指纹、快照或其他机制以及单次读取期间变化的处理，留待实现设计。仅用时间戳不能保证一致性。本节不承诺已实现版本检查，也不要求每次变化都重读全文。

用户已正确回答：文件变化后不能把旧片段当作当前代码直接修改，否则可能破坏程序。该题通过；版本检查具体机制仍未定稿。

## 10. read_file 阶段小结与 search_code 入口

read_file 已完成输入、原文输出、错误区别、分段范围及版本一致性的概念教学。默认值、资源上限、部分边界行为及版本实现尚待统一收束，不标为可直接实现的完整协议。

search_code 的首版教学方案：在授权范围内按明确文本查找候选位置，返回路径、行号和匹配片段，供 Agent 决定下一次 read_file 的目标。文本命中不等于语义调用关系，也不证明 Bug 所在；读完整相关逻辑后才分析。

本节以函数名 calculate_price 的定义、调用和测试命中为例。用户回答查看 price 附近，未定位到调用处；导师补充位置参数按顺序对应形参、检查参数来源应读调用处的原理，未记为独立答对。

## 11. search_code 输入与结果草案（教学中）

已确认输入：query（明确的非空文本）、scope（项目内相对范围，默认 `.`）、max_results（默认 20，范围 1～100）。V0.1 使用 Python 原生能力进行大小写敏感的字面文本匹配，只搜索 `.py` 文件；单文件 scope 指向其他类型时明确拒绝，不把未搜索冒充成零匹配。首版不提供正则、忽略大小写或 AST 语义搜索。

单个候选文件读取上限为 64 KiB，并按 UTF-8 文本处理；超限、无法读取、无法解码或路径越界的候选被跳过，同时把结果标记为不完整。

结果表达实际范围、项目相对路径、从 1 开始的行号、匹配行、返回数量及是否完整。候选路径和文件内行号采用确定顺序。最多返回 20 条不等于项目只有 20 条；发现第 21 条或部分文件无法读取时，不能暗示搜索已完整覆盖，并应提供稳定的不完整原因。

成功搜索但零匹配，不同于搜索执行失败；结论限定为本次查询、实际覆盖范围和匹配规则内未发现匹配。不能据此断言项目不存在相关功能，也不能掩盖未搜索或无法读取部分。

用户已正确回答：零匹配可能来自命名不同或目录范围不对，应调整搜索词或范围继续调查。该题通过。

## 12. edit_file 精确替换草案（教学中）

首版候选：修改一个已有文本文件中的一处明确内容，不接受“帮我修好”等自然语言指令自行决策。输入讨论为 path、old_text、new_text；版本前置条件与具体 Schema 后续收束。

Runtime 先检查参数、目标及授权；工具对当前内容进行精确匹配，old_text 必须非空且恰好匹配一次才可按请求替换。0 处匹配返回目标内容不匹配，不能直接推断具体原因；多处匹配返回歧义，不默认替换第一处或全部。可由 Agent 读取当前上下文后扩大原文片段来准确定位。

空白、缩进也是精确匹配内容的一部分，不做隐式模糊修正。唯一匹配不证明修改符合业务需求，也不能替代权限及版本条件检查。文件不存在时不自动创建。

成功结果应提供实际修改的路径与变化摘要/差异，不能仅凭请求记录成功；原文校验不通过时不写入。写入中失败的恢复与原子性后续设计，不把所有失败均表述为文件完全未变化。

用户已正确回答多处命中应返回匹配歧义并说明理由；扩大原文上下文使目标唯一由导师补充，不记为用户独立答出。草案未最终确认或实现。

## 13. edit_file 写入过程与差异（教学草案）

直接清空目标后逐步写入，可能在中途失败时留下不完整文件。候选流程：读取并检查原文和授权 → 在内存构造完整候选内容 → 在同目录临时文件写入完整内容并检查写入结果 → 确认目标仍符合修改前置条件 → 使用平台支持的替换操作更新目标 → 记录实际结果。

原子替换的目标是在支持的操作系统和文件系统条件下，使目标路径从旧完整内容切换到新完整内容，避免暴露半写文件。它不等于断电持久性保证、并发冲突保护或多文件事务；具体平台 API、权限保留、同步落盘和竞争处理留待实现阶段核实，当前不承诺任意故障下必然不变。

临时文件写入失败且尚未替换目标时，这次尝试没有写入目标，不能记录修改成功；若替换是否完成无法确定，应核对目标后报告已确认事实，不盲目重试或声称原文件未变。

diff 表达修改前后实际内容的差异，用于审查、记录和辅助恢复判断，不自动证明业务正确，也不是完整备份或回滚机制。预览 diff 是计划修改，只有执行确认后才能记为实际修改。默认不自动恢复可能包含用户新改动的文件。

用户已正确回答：临时文件写入失败且尚未替换目标时，原文件未被本次操作修改，应反馈实际错误。该题通过。

## 14. run_tests 契约入口（教学草案）

职责：按明确目标执行已配置的测试方式，返回实际执行证据，不自行修改代码、安装依赖或判定整个任务完成。

候选输入为测试目标及超时限制；测试运行器、项目根目录和环境由项目配置确定。Agent 选择目标，不以任意 shell 字符串替代受约束接口；配置及具体字段后续确定。Runtime 仍检查授权范围，测试会执行项目代码，不自动视为只读操作。

结果概念上分为运行情况与测试结果：是否启动、是否结束/超时、实际测试目标、退出信息、可确认的用例统计及必要失败详情。统计无法取得时标为未知，不能填零。日志受限时说明截断；具体限制和解析方式后续设计。

区分未能启动、启动但收集/环境阶段出错、用例运行后有失败、测试通过、未发现测试及超时等情况。测试进程启动不等于用例已执行；没有失败报告不等于通过。例：5 条用例中 3 通过、2 失败，应记录实际运行及失败证据，不记为测试未启动，也不宣称任务完成。

用户已正确回答：发现 0 条测试不能记录验证通过，因为没有测试用例实际提供通过证据。该题通过；还需由 Agent 检查测试目标与配置，不能立即断言项目没有测试。所有数字是教学示例，未实际运行测试。

## 15. run_command 契约入口（教学草案）

职责：在任务项目的受控环境中执行一个明确允许的程序及参数，返回实际进程结果。它用于运行应用、静态检查或当前专用工具尚未覆盖的必要命令，不替代 run_tests 的结构化测试结果，也不自行安装依赖、修改命令或决定任务完成。

输入概念上至少包含：program（要启动的程序）、args（参数列表）、working_directory（项目根目录内的工作目录）、timeout（最长运行时间）。首版倾向于程序与参数分开传递，不接收一整段交给 shell 解释的字符串；允许程序、参数、目录、环境变量和超时上限均由 Runtime 按策略检查。具体白名单及字段后续定稿。

工作目录会影响相对路径、配置和导入结果，因此必须明确且限制在任务项目范围。环境变量首版只允许受控集合，不能默认把秘密或整个宿主环境暴露给进程。命令即使看似只读，也可能执行项目代码产生副作用，风险根据操作、目标、范围和可恢复性判断。

结果应区分：是否启动、是否正常结束、退出码、标准输出、标准错误、是否超时以及输出是否截断。退出码 0 通常只说明进程按自身约定成功结束，不能自动证明用户任务完成；非 0 也应保留输出供 Agent 判断。超时时需终止受控进程并准确报告，子进程清理细节留待实现设计。

用户对为何不接收任意 Shell 字符串回答不知道。已讲解 Shell 会解释连接、管道、重定向、变量展开等语法，使一段文本可能包含多个操作；program 与 args 分开并使用不经过 Shell 的进程接口，可减少额外解释并便于逐项校验。该知识点记为经讲解，不记为独立答对。即使分开传递，仍需程序白名单、参数规则、目录、权限、环境及超时检查。

运行命令的授权范围应绑定具体程序、参数、目录和任务。用户已正确回答：只授权 `python app.py` 不能直接用于 `python cleanup.py`，即使解释器相同，脚本及潜在行为已经改变。该题通过。

参数、工作目录或环境变化可能改变操作含义，超出原授权时必须重新检查并按风险请求确认。授权记录不应简化成“允许 Python”，也不因一次允许而永久放行相同程序。Runtime 依据实际请求逐项匹配授权范围。

run_command 的核心概念教学已覆盖程序与参数分离、工作目录、受控环境、超时、进程结果和具体授权范围。白名单、输出上限、子进程清理、平台差异和具体 Schema 尚未定稿或实现。

## 17. edit_file V0.1 最终协议（2026-09-24）

`edit_file` 只修改项目根目录内已经存在、最大 64 KiB 的 UTF-8 文本文件。输入固定为非空 `path`、非空 `old_text`、必填但可为空的 `new_text`，以及基于完整原始字节计算的必填 `expected_version`。V0.1 不创建文件，不支持正则、模糊匹配、全部替换或多文件事务。

每个 AcceptedEditFileToolAction 都需要独立权限请求。待确认请求保存完整参数快照，用户决定通过 permission_request_id、task_id 和 action_id 关联；批准后 Runtime 从 State 取回原始不可变 Action，不能根据回答重新生成或扩大修改范围。

执行时先检查项目路径和无变化请求。路径逃逸或 `old_text == new_text` 在 Tool 调用前登记 rejected。Tool 读取真实字节后校验版本、UTF-8 编码和精确匹配数；0 次、多次匹配或版本变化均登记 failed，且不写入目标文件。

唯一匹配时，Tool 根据同一快照生成新字节、前后 SHA-256 版本和 unified diff。写回使用目标同目录临时文件，完整写入后执行 flush、fsync、复制权限并再次核对目标版本，最后调用 `os.replace` 切换。替换前失败会清理本次临时文件并保留目标文件。

成功结果包含 path、before_version、after_version、固定为 1 的 replacement_count 和真实 diff。只有原子替换完成后才能登记 success。该实现不承诺断电后的目录项持久性、多进程完全无竞争或多文件事务。

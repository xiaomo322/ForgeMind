# ForgeMind Agent 架构设计

**版本：V0.1**  
**状态：架构深化中；已讲解决策输入，具体实现待定**

## 1. Agent 定位

Agent 是 ForgeMind 的思考和决策者，不直接替代工具执行项目操作。

## 2. 核心职责

- 理解用户需求；
- 分析项目和任务相关代码；
- 识别候选问题与已确认问题；
- 制定解决方案；
- 选择下一步 Action 和 Tool；
- 判断决策风险与是否需要用户确认；
- 根据 Observation 更新认知；
- 判断任务是否完成。

## 3. 决策原则

```text
小决策 → Agent 自主继续
大决策 → 用户确认后继续
风险不明确 → 按高风险处理并请求确认
```

## 4. 认知状态

问题判断可以经历：

```text
未知 → 候选 → 怀疑 → 验证 → 确认
```

Agent 不应把尚未验证的候选问题当作已确认事实。

## 5. 安全边界

Agent 可以先进行风险判断，但 LLM 判断不构成最终安全边界。所有 Tool 调用都必须经过 Runtime 的确定性校验，高风险操作还需相应的明确授权。

## 6. 每轮决策所需输入

- 任务目标：用户要解决什么问题，以及完成要求。
- 当前证据与进度：相关文件内容、已执行操作、实际结果、待验证或已否定的推测。
- 工具说明：可用工具的用途与调用要求；说明某项能力不等于授予使用权限。
- 行为规则与约束：证据要求、任务范围、权限及用户确认情况。

每轮需要显式提供当前决策所需的上下文，不假定模型自动保留前轮记录。用户已正确指出：缺少进度可能导致重复操作、陷入循环，并影响正确修复。记录充分能降低此类风险，但不保证决策必然正确。

## 7. 当前课程位置

已完成决策输入、上下文遗漏拒绝记录及业务规则不明确时询问用户的理解检查。Action 练习中用户理解应反馈缺失参数且不能猜测；主动搜索补足证据由导师补充讲解，尚未独立验证。当前学习 Observation 如何表达执行阶段与实际结果，具体字段和协议仍待后续设计。

## 8. 本轮上下文与真实授权记录

State 保存的信息不等于每轮实际提供给模型的信息。整理上下文应保留目标、相关证据、进度、有效约束及重要的否定结果，省略无关详情时不能把推测改写成事实。

用户已指出：遗漏用户拒绝记录，Agent 可能重复请求修改，而 Runtime 应依据拒绝记录阻止执行。Runtime 查询真实授权记录，不能仅依据给模型的摘要判断权限。上下文遗漏不能改变授权状态。

已补充讲解：拒绝某次操作不一定终止整个任务；Agent 可以评估符合约束的其他方案，确无可行路径时说明阻塞，不反复索取同一授权。

## 9. 决策输出分类（已讲解，协议待定）

- 调用工具：表达明确操作，由 Runtime 校验并调度；结果记录后继续决策。
- 询问用户：表达需要补充的信息或需要用户选择的事项，Runtime 保存等待状态并呈现问题，收到回答后恢复。
- 提出完成：给出结果、验证依据和未验证事项，Runtime 根据已有执行记录及约定规则处理完成请求；不能仅凭模型自称成功判定任务完成。

权限确认还可以由 Runtime 在处理工具请求时主动触发，不依赖 Agent 自觉询问。上述三类是当前决策输出的概念分类，不替代 Runtime 的取消、错误、上限等控制分支。具体枚举与 Schema 留待后续设计。

用户已正确选择：会员折扣与优惠券能否叠加没有需求依据时，应先询问用户，避免实现不符合用户意图的规则。已讲解信息来源的区别：现有行为查项目证据，未规定的预期行为询问用户，执行权限由 Runtime 检查。

## 10. 从决策到明确 Action（本节教学内容）

操作请求应明确表达请求类型、工具、工具所需参数和理由；沿用既有 action_id、action_type、tool_name、arguments、target、reason 的初步讨论，不在本节定稿字段或所有输出类型的统一结构。

例如读取 pricing.py，需要明确工具为 read_file、文件目标为 pricing.py；“查看价格相关代码”仍可能需要先搜索，不能由 Runtime 猜测文件名。理由用于解释决策，不替代参数，也不授予权限。

Runtime 按工具契约校验请求，缺少必填参数时返回明确错误，不调用 LLM 补全，也不执行工具。Agent 根据错误及现有证据修正请求；信息可通过工具获取时不必直接转问用户。结构完整仍需权限等检查，不等于执行已成功。用户已理解反馈缺失参数与不猜测原则；未知路径时先搜索由导师补充讲解。

## 11. Observation 的信息职责（教学方案）

Observation 向 Agent 反馈一次请求的实际处理情况。工具执行结果可以形成 Observation；请求在参数或权限检查阶段被拦截时，Runtime 也应提供明确反馈，不能假装工具已经执行。

概念上需要表达：对应哪次请求、处理阶段、工具是否执行、实际结果或错误类别、支持判断的必要详情。具体字段名和状态枚举不在本节定稿。

- 参数不完整：工具未执行，反馈缺少的参数。
- 权限不允许：工具未执行，反馈权限原因；缺少授权与明确拒绝应保留区别，不通过修改路径等方式绕过约束。
- 读取文件时返回文件不存在：工具已尝试读取但未成功取得内容，反馈路径及实际错误；失败本身不证明文件为何不存在。

运行测试还需区分工具是否成功启动测试与测试用例是否通过，不能把测试失败自动等同于工具未能运行。Agent 根据事实决定下一步，Observation 不代替业务决策。用户正确指出拒绝原因，但将调用前拦截误判为已执行失败；已讲解纠正为工具未执行，不记为完全独立答对。

## 12. 一轮请求的完整记录（教学示例）

场景：用户已拒绝针对 pricing.py 的某次具体修改，Agent 再次提出同一操作。Action 只表达请求，不证明操作发生。Runtime 在授权检查阶段拦截且不调用工具，形成对应请求的 Observation：请求被拒绝、工具未执行、原因是用户拒绝该操作。

Runtime 更新 State 时保留该次请求及拒绝结果，不能新增成功修改记录；历史修改记录不因这次拒绝而删除，也不能据此断言文件从未被其他操作改变。Agent 下一轮依据记录评估允许的替代方案，确无可行路径时报告阻塞。

Action、结果记录通过请求标识建立对应关系，用于区分多次操作；不在此定稿字段类型或完整 Schema。工具已调用也不等于目标副作用发生，实际修改情况仍以执行证据为准。

本节用记录表串联请求、校验、反馈、状态更新和后续决策；示例未在项目实际执行。用户已正确回答：文件不存在时记录尝试读取但失败及其原因，不能记录成功读取。该题通过，基本决策过程已讲解，课程进入 05 read_file 契约设计；不表示 04 所有实现细节已定稿。
